1. System module overview

This shows how the major modules connect. The detailed ER diagrams are split below to keep the design readable.

2. Identity, organizations, KYC, CRM and rate request

This area controls who can use the system, which customers/agents/carriers exist, and how sales inquiries become rate requests.

3. Rates, quotations, shipment core, booking and INTTRA references

This is the commercial-to-operational handover. Accepted quotations create shipments. Shipments create bookings. INTTRA references are stored as external provider references.

4. SI, BL, containers, cut-offs, tracking and documents

This is the main logistics operations area: SI collection, BL draft/final versions, release orders, containers, shipment events, and file/document control.

5. Workflow, approvals, plug-ins, AI tools and audit

The workflow engine controls states and approvals. Plugins connect external systems such as INTTRA. AI tools are permission-controlled and every tool call is logged.

6. Important design notes

INTTRA is a plug-in

INTTRA should not own your shipment data. The CLS system remains the source of truth; INTTRA stores external booking/rate/tracking references.

Use external_references

Store INTTRA booking references, carrier booking references, BL numbers, and container references without mixing them into every table.

Use versions for SI and BL

SI and BL can change many times. Keep versions so you can audit what changed and who approved it.

Workflow controls risk

BL release, Switch BL, booking cancel, and booking amendments should go through workflow states and approval requests.

AI cannot bypass permissions

AI tool calls should be checked using the same user permissions, workflow status, and approval rules as normal UI actions.

Documents are linked generically

A document can link to a shipment, SI, BL, booking, customer, or approval using document_links.
